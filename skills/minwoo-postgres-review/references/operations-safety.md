# DB 변경·권한·복구 검토

마이그레이션, 접근 제어, 복구 준비를 검토할 때 필요한 항목만 적용한다. 단순 조회나 쿼리 튜닝에 전체 절차를 강제하지 않는다. 아래는 작업 지침이며 DB 권한을 강제로 제한하는 장치는 아니다.

## 대상과 권한

- 프로젝트의 DB 엔진·버전, ORM·CLI의 잠금 버전, 실제 연결 대상(환경·프로젝트·DB·스키마·브랜치)과 현재 역할을 대조한다. 파일 이름의 dev나 기본 CLI 컨텍스트만 믿지 않는다. 연결 문자열·비밀번호·실제 고객 값은 보고서에 출력하지 않는다.
- PostgreSQL에서는 허용된 연결에서 `current_database()`, `session_user`, `current_user`와 역할 속성·상속·객체 소유권을 확인할 수 있다. 이 값만으로 운영/개발을 확정하지 말고 프로젝트의 대상 식별 정보와 함께 확인한다. 역할 이름이 readonly여도 실제 권한은 별도다.
- 조사 전용·앱 실행·스키마 변경 계정의 역할을 구분한다. 소유자·슈퍼유저·BYPASSRLS 및 상속 가능한 관리 역할은 읽기 전용·RLS 검증 계정으로 적합하지 않다. SELECT 권한만 살펴보고 안전하다고 결론 내리지 말고 함수 EXECUTE, SECURITY DEFINER, PUBLIC 권한도 관련 범위에서 검토한다.
- 기존 사용자 승인과 대상 범위가 충분하면 계속 진행한다. 외부 스킬의 매 단계 재승인·변경 ID 제도는 가져오지 않는다. 대상이 불일치하거나 중요한 데이터 손실 위험의 권한이 불명확한 경우 실행을 멈추고 구체적인 변경안으로 확인한다. 도구의 실행 권한이나 이 문서 자체를 운영 DB 변경 허가로 해석하지 않는다.

## 변경 전후의 증거

- 현재 프로젝트의 마이그레이션 흐름으로 SQL·차이를 먼저 검토한다. 생성/계획 명령도 개발 DB나 shadow DB를 초기화·변경하는지 해당 버전 문서와 옵션에서 확인한다. 연결 복구를 이유로 ORM을 업그레이드하거나 DB를 새로 만들지 않는다.
- UPDATE/DELETE의 조건, 예상 대상 수와 주요 값, DROP·형 변환의 손실, 제약·인덱스·잠금·테이블 재작성·앱 구버전 호환성을 확인한다. WHERE가 있다는 사실만으로 안전하지 않으며 사전 SELECT와 실행 사이에 데이터가 바뀔 수 있다. 필요한 트랜잭션·동시성 통제를 프로젝트에 맞춘다.
- 큰 변경은 확장→이행→정리처럼 호환되는 단계가 가능한지 검토한다. 잠금·문장 제한 시간과 중단 조건은 환경에 맞게 정한다. 모든 DDL을 한 트랜잭션으로 묶을 수 있다고 가정하지 않는다.
- 계획 조회와 실제 실행을 구분한다. EXPLAIN ANALYZE는 쿼리를 실행하고, SELECT도 함수 부작용이 있을 수 있다. ROLLBACK이 외부 호출·시퀀스 등 모든 효과를 되돌린다고 가정하지 않는다.
- 격리 환경은 합성 데이터가 기본이다. 실제 데이터가 필요하면 허용된 범위·마스킹·보관 정책을 확인한다. 클라우드 브랜치 생성·복제·복원은 외부 쓰기/비용/데이터 복제 행위일 수 있으며 단순 검토에 자동 추가하지 않는다.
- 실행 후 실제 데이터 값·제약·권한·앱 주요 경로와 마이그레이션 이력을 확인한다. 종료 코드 0이나 같은 행 개수만으로 데이터 보존을 판정하지 않는다. 실패한 마이그레이션을 무작정 재실행하거나 이력을 성공으로 표시하지 않는다.

## RLS와 최소 권한 확인

소유자/슈퍼유저가 아닌 실제 앱 역할로 허용과 차단을 모두 확인한다. 익명/로그인, 본인/다른 사용자, 읽기/쓰기, 소유자 필드 변경 등 이번 변경에 관련된 경로를 고른다. UPDATE가 오류 없이 0행인 경우와 성공한 경우도 구분한다.

RLS는 테이블 접근 권한을 부여하지 않고 TRUNCATE를 제한하지도 않는다. 쓰기 차단은 실제 역할 권한으로 확인한다. Supabase의 service_role·JWT·auth 함수·뷰·Storage 정책은 로컬 역할 흉내만으로 검증 완료라고 하지 않는다. 권한 오류 해결을 위해 RLS 비활성화나 관리자 계정 전환을 자동 적용하지 않는다.

## 복구 준비와 복원 시험

- 백업의 존재, 성공 시각·대상·보존 기간·복구 가능한 시점과 실제 복원 이력을 구분한다. 허용 가능한 데이터 손실 시간(RPO)과 복구 시간(RTO)에 맞는지 확인한다. 보이지 않는 증거는 미확인으로 남긴다.
- down SQL은 스키마를 되돌려도 삭제·변환된 데이터를 되살리지 못할 수 있다. 롤백·전진 수정·백업/PITR 복구 중 가능한 경로와 그 한계를 명시한다. 운영 복원·접속 전환은 별도의 실제 변경이다.
- 복원 시험이 요청·허용된 경우 원본을 덮어쓰지 않는 새 격리 대상으로 복구한다. 주요 값·제약·역할·RLS·앱 읽기/쓰기 및 필요한 확장·외부 저장소 의존성을 확인한다. 복구 시간도 실제 측정한 범위만 기록한다.
- PGlite의 메모리 SQL·스냅샷 복원 시험은 기본 동작의 예시다. 운영 PostgreSQL 백업, WAL/PITR, 동시 접속·잠금, Supabase 인증, 클라우드 장애 전환을 검증한 것으로 확대하지 않는다.

결과에는 대상(비밀값 제외), 확인 근거, 실행한 변경, 데이터/권한 검사, 복구 검증 범위와 미확인 항목을 짧게 남긴다. 실행하지 않은 변경을 완료로 적지 않는다.

## 근거와 범위

직접 작성한 공통 절차다. PostgreSQL 공식 [권한](https://www.postgresql.org/docs/18/ddl-priv.html), [행 보안](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [덤프·복원](https://www.postgresql.org/docs/18/backup-dump.html)을 기준으로 하며 대상 버전 문서를 다시 확인한다. 서비스별 원본의 검토 커밋·조건은 kit의 DB 참고 후보 안내에 따로 기록한다. 외부 승인 계약·자동 설치 지시는 이 절차에 편입하지 않았다.
