# 로그·측정·요청 추적 구현

먼저 답하려는 운영 질문을 정한다. 어떤 요청이 느린지, 어느 단계에서 실패했는지처럼 필요한 증거에 맞춰 기존 로깅·계측을 확장한다. 로그 수집 서비스나 OpenTelemetry 설치부터 시작하지 않는다.

- 로그는 개별 사건, 측정값은 집계, trace는 요청의 여러 단계 연결에 맞춰 선택한다. 같은 정보를 모든 방식으로 중복 기록하지 않는다. 상관 ID를 보존하되 사용자 제공 ID를 신뢰할 수 있는 인증 정보처럼 쓰지 않는다.
- 시간 측정은 단조 시계를 사용하고 성공·실패·취소 경로에서도 종료 처리를 보장한다. 예외를 기록한 뒤 삼키거나 반환 의미를 바꾸지 않는다. 동시 요청의 context가 섞이지 않게 전달한다.
- 허용한 필드만 기록한다. 토큰·쿠키·요청 본문·개인정보를 통째로 수집하지 않는다. URL query나 오류 문자열도 민감할 수 있다. metric label에는 사용자 ID·원문 URL처럼 종류가 끝없이 늘어나는 값을 넣지 않는다.
- 수집량·샘플링·보관·오버헤드를 목적에 맞게 제한한다. exporter/로그 sink 실패가 앱 실패를 덮어쓰거나 요청을 끝없이 기다리게 하지 않도록 한다. 운영 수집·외부 전송은 해당 요청에 허용된 범위에서만 한다.
- 로컬 sink나 메모리 exporter로 성공·실패·동시성·민감 필드 제외·수집기 장애를 시험한다. 로그가 한 줄 나오는 것을 실제 운영 수집·경보 성공으로 보고하지 않는다.

보고에는 계측 위치, 실제 기록 필드와 단위, 수집 범위, 실패 시 동작, 검증 결과를 남긴다. 기존 오류를 조사하는 목적이면 diagnosing-bugs가 주도하고 이 스킬은 필요한 계측 구현만 맡는다. 고객 행동 분석·추적 코드를 임의 추가하지 않는다.
