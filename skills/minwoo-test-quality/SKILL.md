# 테스트 검증력 점검

테스트가 통과하는 사실과 결함을 잡는 능력을 구분한다. 요청된 코드·공개 동작·실패 위험을 정하고 기존 테스트를 먼저 실행한다. 이미 실패하는 테스트나 실행할 수 없는 환경을 변이 결과와 섞지 않는다.

- 테스트 이름보다 실제 assertion과 호출 경로를 본다. 반환값·부작용·오류 조건·권한 경계 중 해당 계약에 필요한 것을 검증하는지 확인한다. 구현과 같은 계산을 기대값으로 복제하지 않는다.
- 누락한 경계·분기·실패 처리를 구체적인 결함 예로 설명한다. 줄 커버리지나 테스트 개수만으로 품질을 판단하지 않는다. mock이 대상 동작까지 대신해서 항상 통과하는지 확인한다.
- 의심되는 부분에 작은 결함을 주입하고 테스트가 실패하는지 확인할 수 있다. 원본을 손상하지 않도록 격리 사본 또는 프로젝트가 쓰는 변이 도구를 사용한다. 돌연변이 하나의 결과를 전체 변이 점수로 표현하지 않는다.
- 변이는 타깃·횟수·시간을 제한한다. 실행 실패·타임아웃·미실행·살아남은 변이·같은 의미의 변이를 구분한다. 테스트가 해당 코드까지 갔는지 확인하고 의미가 같은 변이를 잡으려고 요구사항을 왜곡하지 않는다.
- 필요한 assertion을 보강하고 정상 구현의 통과, 관련 결함의 실패를 함께 확인한다. 기존 테스트 삭제·무조건 skip·타임아웃 증가로 성공을 만들지 않는다. 읽기 전용 요청이면 수정 제안까지만 한다.

Stryker 등 새 도구를 필수로 설치하지 않는다. 기존 실행기로 작은 수동 변이를 확인할 수 있고, 도구를 도입할 때는 프로젝트 언어·버전·비용을 확인한다. 보고에는 실제 시험한 결함과 범위, 살아남은 변이의 해석, 미실행 부분을 남긴다.

불변식·랜덤 입력 생성이 핵심이면 minwoo-property-testing, 가끔 실패하는 원인 분석이면 diagnosing-bugs가 주도한다. 테스트 우선 기능 개발 전체를 다시 시작하지 않는다.
