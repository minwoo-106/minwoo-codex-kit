# 측정값과 변이의 해석

테스트 검증력·복잡도·중복 지표를 함께 검토할 때 읽는다.

- 커버리지·복잡도·중복 수치에는 도구/버전, 대상 경로, 생성 코드·테스트 제외 기준과 기준 커밋을 붙인다. 서로 다른 설정에서 나온 수치를 그대로 전후 비교하지 않는다.
- 높은 커버리지와 낮은 복잡도는 결함 탐지의 증거가 아니다. 위험한 경계의 assertion과 실제 호출을 확인하고, 요청에 맞는 작은 변이로 검증한다.
- 정상 코드가 통과한 같은 테스트 명령으로 의미 있는 결함을 넣었을 때 assertion이 실패하는지 확인한다. import 오류·환경 실패·타임아웃을 결함 탐지 성공으로 세지 않는다. 실패의 이유가 기대한 계약 위반인지 확인한다.
- 살아남은 변이는 코드 미도달, assertion 누락, 의미가 같은 변이, 실행 도구 문제를 구분한다. 무조건 모든 변이를 죽이려고 공개 동작·테스트 기준을 바꾸지 않는다.
- 숫자를 맞추기 위해 함수만 잘게 쪼개거나 분기·검사를 삭제하지 않는다. 프로젝트가 이미 정한 기준이 있으면 따른다. 원본의 CRAP < 10·중복 유사도 0.8을 모든 언어의 공통 규칙으로 추가하지 않는다.
- 변이 도구나 복잡도 계산기는 실제 반복 수요가 있을 때 도입한다. 새 도구 없이 격리 사본에서 확인한 작은 사례를 전체 품질 점수로 확대하지 않는다.

[ub-mode](https://github.com/unclebob/ub-mode/blob/3da62bf3fcfd2034de41f30d920d2739e566171f/SKILL.md)의 도구 기반 검증 관점을 참고해 직접 작성했다. 동반 crapper/dryer/mutator/uml-viewer는 이름을 확인한 단계이며 각각의 코드·배포·라이선스를 검수/설치한 상태가 아니다. 자동 설치·매 작업 기록·기본 브랜치 푸시 지시는 가져오지 않았다.
