# 웹과 UI 선택

## 결과물 위치부터 결정

- 기존 저장소의 화면 수정·로컬 코드 납품이면 그 프로젝트와 프레임워크를 유지한다. Sites로 임의 이전하거나 배포하지 않는다.
- 새 웹사이트 제작·기존 Sites 편집·Sites 호스팅 요청이면 현재 제공되는 sites:sites를 먼저 확인한다. 로컬 전용 요청은 그 스킬의 로컬 경로를 따른다.
- 기존 Site를 복제·변형하는 요청은 sites:sites-remix를 추가한다.
- Higgsfield 호스팅을 지정하면 app-6a3293e129088191abf0875820e839da:website-builder를 쓴다. 같은 사이트를 Sites와 Higgsfield 양쪽에 만들지 않는다.
- Figma 시안이 입력이거나 결과물이라면 [Figma 안내](figma.md)를 읽는다.

## 주도 스킬 하나 고르기

| 상황 | 주도 | 추가할 때 / 겹침 제외 |
| --- | --- | --- |
| 브랜드·포트폴리오·랜딩의 뚜렷한 시각 방향 | design-taste-frontend | frontend-design과 두 가지 스타일 체계를 동시에 강제하지 않음 |
| 작은 새 UI, 가벼운 시각 지침으로 충분 | frontend-design | 큰 디자인 조사 절차를 필요 없이 추가하지 않음 |
| 기존 UI의 계층·여백·반응형·접근성 개선 | impeccable | 필요한 critique/polish/adapt 등만 사용; 전체 명령 순회 금지 |
| 색·폰트·UX 근거가 부족 | ui-ux-pro-max를 보조로 | 근거 검색 결과를 프로젝트의 확정 디자인보다 우선하지 않음 |

선택한 방향·색·폰트·간격·컴포넌트 규칙은 기존 DESIGN.md 또는 프로젝트의 기존 디자인 문서에 필요한 만큼 남긴다. 21st 프로젝트라면 그 스킬의 .21st 문서를 활용한다. 같은 결정을 여러 파일에 중복 기록하거나 사소한 수정마다 새 문서를 만들지 않는다.

## 21st 역할 분담

- 21st-ui-explore: 디자인 방향이 미정이고 여러 안 비교가 필요한 경우.
- 21st-cli-use: 카탈로그에서 특정 컴포넌트·테마를 검색·가져오는 경우.
- 21st-ui-build: 21st를 활용해 프로젝트 맥락에 맞는 화면을 구현하는 경우.
- 21st-ui-review: 21st 중심의 화면 검토만 요청한 경우. impeccable과 같은 항목을 중복 전수 검사하지 않는다.
- 21st-ai: 21st 생성·변형 기능을 사용하는 요청. 현재 기능 접근과 크레딧 조건을 확인한다.
- 21st-registry: 사용자가 구성 요소·테마의 레지스트리 게시·관리를 요청한 경우에만.

## 검증은 목적에 맞게

시각 품질은 렌더된 화면을 보고 평가한다. minwoo-browser-check는 버튼·폼·검색 등 동작과 회귀 증거를 맡으며 디자인 평가를 대체하지 않는다. 단순 폰트 수정에 전체 브라우저 테스트를 강제하지 않는다.
React 성능 문제는 minwoo-react-performance, 재사용 컴포넌트 API 문제는 minwoo-react-composition을 해당 단계에만 추가한다.
예: 기존 브랜드 사이트 개편은 방향 결정 → 기존 코드 구현 → 필요한 화면 검토 → 주요 동작 검사다. 이 순서를 이유로 모든 디자인 스킬을 로드하지 않는다.
